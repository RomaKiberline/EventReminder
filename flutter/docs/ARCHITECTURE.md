# Архітектура системи

За лабораторною №4 використовується офлайн-first багатошаровий Flutter-клієнт:

```text
Користувач → Presentation (Flutter views, event editor)
                       ↓
                 Application (AppController)
                    ↙           ↘
           Domain (Event,          Infrastructure
           Category, recurrence)   NotificationService / BackupService
                    ↓
            IEventRepository ← SqliteEventRepository
                                        ↓
                                  SqliteDatabase
                                        ↓
                                7 SQLite tables
```

Основні інтерфейси та доменні моделі не залежать від Flutter UI. SQLite має зовнішні ключі, CHECK-обмеження, UNIQUE, CASCADE і транзакції. ER-діаграма наведена в `ER_diagram.png`.

**Відмінність щодо еталонної БД лабораторної №5:** база у застосунку створюється з ідентичним набором таблиць і основних атрибутів; тестові демонстраційні рядки із SQL-скрипта не імпортуються автоматично, оскільки застосунок стартує з порожнім календарем та чотирма стандартними категоріями. `Lab5_reference_schema.sql` слугує окремим навчальним SQL-скриптом із демонстраційними записами.

## Подальша розробка

* Відкладені нагадування повинні зберігатися як окремі планування в SQLite, щоб переживати повторне перепланування під час синхронізації.
* Для розгорнутого редагування одиничних входжень серій потрібно додати override-атрибути опису, категорії, місця у `event_exceptions` із міграцією БД (версія 2).
* Для довгострокових повторювань потрібне періодичне фонове поповнення 90-денного вікна сповіщень (WorkManager / BGTaskScheduler).
* Фактичну продуктивність і поведінку сповіщень потрібно перевірити на реальних Android та iOS пристроях.
